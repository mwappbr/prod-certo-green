## Débitos concretos observados

### 1. Proxy de desenvolvimento não acompanha `PORT`

- O review triage de 1.1 registrou o destino duplicado `3000` em `client/vite.config.ts` como diferido para 1.2 (`story-tracer-servico-com-api-health-e-spa-vazia-plan.md`, linha 105). Sob a lease, esse destino fixo foi removido; o proxy agora deriva a porta da configuração central.
- Cenário concreto reproduzido antes da correção: com `PORT=33877`, o servidor iniciava na porta 33877, mas chamadas `/api/*` encaminhadas pelo Vite em 5173 seguiam para 3000.
- `server/src/config/index.ts` continua como única autoridade de `PORT` (número), default 3000 e validação 1–65535 via `loadConfig()`. A importação Node-only da configuração foi exercitada com Node 24; o proxy recebe seu target em `vite.config.ts` (contexto Node, sem expor configuração ao bundle browser). Testes cobriram default, override `33877` e valores inválidos.
- **Solução aplicada:** `client/vite.config.ts` usa `PORT` do helper Node-only `scripts/dev-platform-config.mjs` para formar `http://localhost:${PORT}`. Não lê ambiente localmente nem duplica validação/default; a configuração central mantém o default 3000 e a falha para valores inválidos. O build e o dev standalone do client foram validados sem `PORT` exportada.
- `scripts/dev.mjs` importa a configuração central e passa `PORT` validada como string aos dois processos filhos; o helper somente reexporta `PORT`/`loadConfig`, sem lógica de parsing, default, leitura ambiental ou contrato duplicado.
- A tentativa inicial de importar `../server/src/config/index.ts` diretamente do `vite.config.ts` falhou no client typecheck com TS5097 (`allowImportingTsExtensions`). A incompatibilidade foi reportada antes da ampliação; a coordenação autorizou o fallback previsto (`scripts/dev-platform-config.mjs` + `.d.mts`), que passou os typechecks sem alterar tsconfig, config do servidor ou dependências.

### 2. Inicialização local dependia de operador POSIX

- O script raiz usava `&` para iniciar server e Vite (`package.json`, script `dev`); o plano 1.1 já registrava limitação Windows (`story-tracer-servico-com-api-health-e-spa-vazia-plan.md`, linha 88). Esse acoplamento foi removido sem editar README, manifests além do script `dev`, dependências ou lockfiles.
- `package.json` agora preserva o build de `@hn/shared` e chama `node scripts/dev.mjs`. O launcher Node-only/import-safe invoca `process.execPath` com o CLI obtido de `npm_execpath`, inicia os scripts workspace `dev` de `@hn/server` e `@hn/client` com `shell: false`, cwd raiz e stdio herdado, e injeta a porta validada centralmente. A probe dentro de script npm confirmou o caminho real de `npm_execpath` no Node/npm usados.
- O supervisor coordena só os processos criados por ele: trata erro/saída de filho e sinais no pai, encerra o irmão, limita o período gracioso e aplica encerramento forçado se necessário. POSIX/macOS usa grupos próprios; o ramo Windows usa `taskkill /T` no PID do filho e `/F` após timeout. Os ramos de ownership/cleanup POSIX e estratégia simulada Windows foram exercitados em unit tests; Windows nativo não foi executado.
- **TDD e typechecks:** a RED original registrou 8 falhas de 14 (proxy ainda fixo/aceitando `PORT` inválida e launcher ausente); GREEN passou 14/14 em 3 arquivos. Depois do review READONLY, a RED de follow-up (`red-followup.log`) registrou 4 falhas de teste em 14 casos, representando duas lacunas funcionais de cleanup; as outras duas eram problemas de harness (API ausente e matcher de `AggregateError`), não quatro findings independentes. O GREEN após os ajustes do harness passou 15/15 em 2 arquivos focados; o typecheck server (src + testes, sem emit) passou novamente. O typecheck client passou na lease original. A importação direta `.ts` do config central falhou inicialmente com TS5097; após autorização prévia do fallback `.mjs`/`.d.mts`, os typechecks client/server passaram.
- **Smoke POSIX/macOS:** `npm run dev` com `PORT` ausente serviu a SPA em `http://localhost:5173/` e health real pelo proxy em `/api/health`, ambos HTTP 200 com default 3000. Com `PORT=33877`, o servidor escutou nessa porta e o mesmo health pelo proxy respondeu 200. Nos dois casos, o browser exibiu estado vazio por fixture local; sem chamadas externas, erros de console, page errors ou requests falhos não esperados. A única requisição abortada foi `/api/stories` cancelada pelo cleanup normal do React StrictMode e foi registrada separadamente. Cleanup recebeu SIGINT no grupo raiz próprio; launcher/npm terminaram (status 130 esperado pela interrupção) e portas server/Vite ficaram livres.
- `PORT=not-a-number npm run dev` terminou com exit 1 pela validação central antes de iniciar os processos server/client; após os smokes e este gate, portas 3000, 33877 e 5173 estavam livres. `npm run dev -w @hn/client` respondeu HTTP 200 em `localhost:5173` sem `PORT`; `npm run build -w @hn/client` passou sem `PORT`.
- Não afirmar suporte verificado a Windows nem Node 26. A validação de runtime foi feita somente em Node v24.21.0/npm 11.19.0; não houve alteração de dependências nem do requisito de engine.

#### Follow-up autorizado dos findings de cleanup

- **MEDIUM — drain do grupo POSIX:** o cleanup não usa mais o exit do wrapper como prova de que o grupo morreu. Sinaliza somente o próprio PGID, aguarda com polling/deadline limitado, escala de SIGTERM para SIGKILL e marca o grupo fechado apenas após probe quiescente ou `ESRCH`. `EPERM` de signal/probe permanece falha explícita; não há PID scan nem sinalização de processos alheios.
- **LOW — terminador Windows:** a espera por `taskkill.exe` tem deadline; em timeout o launcher encerra somente o helper que ele próprio criou, aguarda bounded close e tenta a força final, com erro explícito se o helper não terminar. Erros assíncronos do helper após o timeout ficam anexados como causa e não impedem a tentativa de `SIGKILL`; o supervisor também limita a espera por qualquer adapter `spawnTaskkill`. O teste é simulado; Windows nativo continua não verificado.
- **RED/GREEN refinada do helper:** `red-taskkill-helper-error.log` + `.status` reproduziu erro `EPERM` no primeiro `kill()` e mostrou que a implementação rejeitava antes de tentar `SIGKILL`. O handler agora preserva o erro, permite a escalada bounded e agrega a causa no resultado de timeout; o teste verifica tanto a chamada forçada quanto a causa preservada. O teste isolado passou (1/1), a suíte focada passou (15/15 em 2 arquivos) e o typecheck server src+tests sem emit passou novamente.
- **LOW — propagação de cleanup:** erros de cleanup agora tornam o processo não-zero e são logados; saída espontânea de qualquer filho, inclusive código zero inesperado, também encerra com não-zero. Handlers de término inesperado, falha de spawn e sinal do pai capturam rejeições; `stop` continua idempotente.
- **Prova POSIX real:** o microfixture isolado `/tmp/hn-1.8-node24-IqTUui/followup-posix/` criou grupo próprio com wrapper que saiu zero enquanto um grandchild Node ignorava SIGTERM. O trace capturou wrapper PID 9049, grandchild PID 9051, `SIGTERM` seguido de `SIGKILL` apenas ao PGID `-9049`, marcador do handler SIGTERM no grandchild e `groupGone: true`. Evidência: `posix-grandchild-followup-final.log` + `.status` (exit 0). Fixture temporária fora da fonte; sem Vite, API, porta, `.env` ou processos alheios.
